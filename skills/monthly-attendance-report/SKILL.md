# 企业考勤月报全流程自动化交付技能 (Monthly Attendance Report SOP)

## 一、 技能概述与核心定位

本 Skill 专门用于处理企业级「月度考勤数据统计、排名与多端报表交付」，实现从原始打卡底表（Excel）到最终全量表、独立业务分表、静态样式固化以及无损打印级 PDF 交付件的**端到端全自动生产**。

具备强健的规则确定性、严谨的人员合规过滤、精细的像素级表格排版，以及**三道强制性前置业务确认关卡**。

---

## 二、 三个强制前置业务确认关卡 (Mandatory Gates)

在执行任何考勤核算与生成脚本之前，Agent **必须严格按顺序执行以下三项前置核验与确认**：

### 关卡 1：花名册自动检索与用户确认 (Gate 1)

> **业务原则**：严禁静默自选花名册；必须让用户对人员档案基准拥有最终把控权。

1. **用户已显式指定花名册**：
   - 若用户在输入指令中已直接提供文件路径或指明文件名（例如：“使用 `〔中台〕员工花名册-OD_zhaohui118278_2026-09-03_10-11-06.xls`”），**直接以此文件为准**，跳过检索步骤。
2. **用户未指定花名册（自动检索与确认）**：
   - 运行内置扫描工具：
     ```bash
     python <skill_path>/scripts/scan_roster.py --dir <project_or_data_dir>
     ```
   - 工具将自动递归检索包含 `花名册`、`OD_`、`roster`、`员工` 的 Excel 文件，解析制表日期、修改时间、工作表名称及预估在册人数，并按最新版本推荐首选。
   - **Agent 必须主动向用户输出格式化提示并等待用户确认**：
     > “🔍 **花名册前置确认**：
     > 在项目中检索到以下疑似花名册文件：
     > 1. 【推荐首选】`〔中台〕员工花名册-OD_zhaohui118278_2026-09-03_10-11-06.xls`（版本日期：2026-09-03，共 4,962 条员工记录）
     > ...
     > 请确认是否使用推荐的花名册作为本期基准？（如需使用其他文件，请直接回复文件路径）”
   - **必须得到用户明确确认后，方可进入下一步。**

---

### 关卡 2：考勤规则增量校验与用户确认 (Gate 2)

> **业务原则**：严禁遇到未知打卡状态时擅自假定权重为 0 或 1；必须拦截并由用户审批新增规则。

1. **自动比对原始打卡底表与规则库**：
   - 运行内置规则校验工具：
     ```bash
     python <skill_path>/scripts/check_rules.py --raw <raw_attendance.xlsx> --rules <skill_path>/config/考勤规则.json
     ```
   - 工具将全量扫描打卡底表（`Sheet0`）中的所有 `上午状态|下午状态` 组合，与现有规则库比对。
2. **若全部匹配**：
   - 输出 `✅ 考勤规则核验通过：全部状态组合均已收录，无新增规则`，自动继续执行。
3. **若发现未收录的新增规则（强制拦截）**：
   - **立即暂停执行流程**，向用户列出具体的未收录组合、出现频次及涉及员工：
     > “⚠️ **考勤规则增量校验拦截：发现未收录的新考勤状态组合！**
     > 在本次打卡底表中扫描到以下未收录的状态组合：
     > 1. 新状态组合：`已哺乳假冲销|正常`（累计出现 21 次，涉及员工：秦雪静）
     > 
     > 请确认上述新组合的出勤折算权重（`1.0` 全天出勤 / `0.5` 半天出勤 / `0.0` 不计出勤）。”
   - 待用户回复权重后，执行规则追加：
     ```bash
     python <skill_path>/scripts/check_rules.py --raw <raw.xlsx> --rules <rules.json> --add "已哺乳假冲销|正常" --weight 1.0
     ```
   - 更新规则库后，方可继续执行后续核算。

---

### 关卡 3：非补签异常打卡审查与确认 (Gate 3)

> **业务原则**：严禁在未确认的情况下遗漏正规请假单在系统边界产生的打卡异常。

1. **自动扫描“标红但非补签”异常**：
   - 在底表中，若某天打卡时间与人脸门禁时间偏差 $> 60$ 分钟（触发红字），但考勤状态不是“已考勤补签”（无黄底）；
   - 这类情况通常发生在**半天请假**时系统自动填充了无打卡机 IP 的假单边界虚拟时间（如 12:00），导致卡人时间脱节。
2. **生成审查清单并向用户请示**：
   - Agent 列出受影响的员工、日期、打卡时间、人脸门禁时间及请假状态，请示用户：
     > “⚠️ **发现 X 笔异常打卡（非补签但因半天请假系统自动填充时间导致）：**
     > 1. `128898` 张月阳 (09-09): 签到 12:00 vs 人脸 13:48，考勤状态【上午请假】
     > ...
     > 是否确认将上述异常记录视同补签进行‘标黄’免责处理？”
   - 经用户确认后，引擎自动将对应单元格置为**浅黄底色（`#FFFFF3CA`）+ 红色文字（`#FFE54C5E`）**。

## 三、 核心业务口径与计算规则

### 1. 人员地域与常驻判定（北京口径）
- 提取花名册中的办公地点字段（如中台花名册 `AF` 列）；
- 包含 `BJ`、`北京` 或 `ABJ1` 的判定为北京常驻人员，予以保留；
- 其余非北京常驻（如上海、广州、苏州、成都、台湾等异地）以及两份花名册均未收录人员予以剔除。

### 2. 人员与业务排除白名单
- **指定人员排除**：根据 `config/exclusions.json` 中的 `excluded_employee_ids` 列表，匹配人员工号与姓名并排除统计（如 `000001 池宇峰`），直接剔除，不计入任何分表与全量；
- **特定业务排除**：根据 `config/exclusions.json` 中的 `excluded_businesses` 列表，匹配归属业务名称的人员直接剔除（如 `完美世界文化`）。

### 3. 组织层级智能拼接与去重规则
花名册部门列提取采用自适应算法：
1. **游戏工作室群/新业务事业群特例**：若业务类别为“游戏业务”，且二级部门为“游戏工作室群”或“新业务事业群”，**从三级部门拼接到五级部门**（呈现为：`工作室 > 项目部 > 组`，如 `黑羽工作室>KIZUNA>美术部`）；
2. **1.1级与业务同名**：若 1.1 级部门与业务类别相同（如均为“游戏业务”或“集团职能”），**从二级部门拼接到四级部门**（呈现为：`中心/办公室 > 大组 > 落地部门`，如 `游戏管理办公室>HRBP A组>BP六部`）；
3. **通用规则**：其余情况从 **1.1 级部门一直拼接到四级部门**；
4. **相邻同名去重与空值跳过**：自动过滤空层级并消除 `A>A` 同名重复。

### 4. 洪恩业务线接入标准（方案 B）
- **全面接入真实人脸打卡数据**：取消历史抑制，B 行（人脸早/晚）正常展示浅蓝色门禁时间（`FF0070C0`）；
- **全面接入 F 列核算**：正常计算人脸修正均工时（保留 2 位小数 `0.00` 格式）；
- **全员按 F 列升序排列**：与集团职能、游戏业务同等标准，全量及分表统一按 F 列升序排序。

### 5. 业务区域与分表标准定义
全量表共分为 **7 个标准业务区域**（按顺序排列，各分表不重复收录重点关注人员）：
1. `重点关注`：固定名单重点关注人员（按 F 升序排列，缺卡者如 110641 保留空坑位）；
2. `游戏业务`：包含游戏业务主线及电竞与平台业务；
3. `集团职能`：包含集团各职能部门、采购供应商中心、体外业务等；
4. `影视业务`：影视业务人员；
5. `虚拟世界`：虚拟世界产品与研发团队；
6. `新业务事业群`：新业务各项目部；
7. `洪恩`：洪恩业务线。

### 6. 单向防作弊异常打卡标红规则
针对每日签到/签退打卡时间：
$$\begin{cases}
\textbf{签到标红 (红色 FFE54C5E)}: & \text{人脸最早识别时间} - \text{实体签到时间} > 60\text{分钟} \quad \text{（人未到、卡先刷）} \\
\textbf{签退标红 (红色 FFE54C5E)}: & \text{实体签退时间} - \text{人脸最晚识别时间} > 60\text{分钟} \quad \text{（人已走、卡延后刷）} \\
\textbf{缺卡 / 当天无人脸数据}: & \text{浅灰色} \quad (\texttt{FF808080}) \\
\textbf{其余正常打卡}: & \text{纯黑实色} \quad (\texttt{FF000000})
\end{cases}$$
- 跨午夜凌晨 4 点前打卡自动归一化加上 24 小时参与比对，杜绝跨午夜误报。
- A 类（签退）、B 类（人脸最晚）、C 类（外出结束）跨午夜次日打卡统一追加 **`(+1)`** 标识。

### 7. 均工时偏差标红预警（G - F > 0.5）
- 全月打卡签到签退均工时（G 列）比人脸修正均工时（F 列）严格大 0.5 小时以上（$G - F > 0.5$），G 列 7 行合并单元格字体标为**红色**（`FFE54C5E`），提示该员工全月刷卡在司时间存在显著虚高偏差。

## 四、 表格视觉与 7 行一组排版规范

1. **7 行一组结构体系**：
   - 每位员工占 7 行：A 类签到签退（合2行）+ B 类人脸（合2行）+ C 类因公外出（合2行）+ **D 类考勤状态（单行）**；
   - 左侧 A~H 列基础档案在纵向**合并 7 行**，I 列依次展示对应的记录项标签（全部左对齐）；
   - 员工组底黑色中粗分割线顺延至第 7 行底部。
2. **C 类（因公外出）颜色规范**：
   - 时间文字显示为**常规黑色纯实色（`#000000`）**，与签到签退保持视觉一致。
3. **D 类（考勤状态）微文本标签规范（纯净白底）**：
   - 彻底清空单元格背景填色（纯净白底，无彩色压迫感）；
   * **出差**：显示为 **`[出差]`**，采用深海青加粗字（`#004085`）；
   * **请假系列（全天与半天统一带【】强调）**：采用深炭黑微粗体字（`#2B2D42`）：
     - 全天请假：**`【全天请假】`**（调休视同请假）
     - 上午请假：**`【上午请假】`**
     - 下午请假：**`【下午请假】`**
   * 其余无请假出差的工作日保持完全空白。
4. **二维冻结窗格**：
   - **全量表**：冻结窗格设为 **`J6`**（纵向冻结第 1~5 行日历表头，横向锁定 A~I 列基础信息）；
   - **7 个业务分表**：冻结窗格设为 **`J7`**（纵向冻结第 1~6 行日历表头与业务大标题，横向锁定 A~I 列）。
5. **静态纯净交付**：
   - 彻底清空 Excel 动态条件格式，所有色彩（红/灰/黑/黄）均由代码直接写入单元格静态属性，确保任何 Excel 版本或移动端打开色值饱满不虚化。
6. **打印级无损 PDF 导出**：
   - 页面横向（Landscape），纸张 Letter，适合宽度 1 页；
   - 智能计算分页符（RowBreak），将 7 行一组作为不可分割原子块分页，绝对防止员工数据跨页被腰斩；
   - 全量表自适应分页为 **14 页**，重点关注表稳定为 **1 页**。

## 五、 端到端标准执行流程 (SOP)

```text
[用户输入] ──> [Gate 1: 扫描/确认花名册] ──> [Gate 2: 增量校验考勤规则] ──> [Gate 3: 确认非补签异常打卡] ──> [运行自动化引擎] ──> [交付 Excel/PDF 及审计对账]
```

### 步骤 1：定位花名册（执行 Gate 1）
- 用户未指明时，调用扫描脚本：
  ```bash
  python <skill_path>/scripts/scan_roster.py --dir .
  ```
- 提示用户确认花名册路径。

### 步骤 2：校验考勤规则（执行 Gate 2）
- 扫描打卡底表：
  ```bash
  python <skill_path>/scripts/check_rules.py --raw "<raw_attendance.xlsx>" --rules "<skill_path>/config/考勤规则.json"
  ```
- 若有未录入规则，询问用户并录入。

### 步骤 3：审查非补签异常并确认标黄（执行 Gate 3）
- 引擎核查是否存在因半天请假等产生的无补签红字异常，提请用户确认是否标黄免责。

### 步骤 4：一键运行交付引擎
- 执行核心生成管线：
  ```bash
  python <skill_path>/scripts/pipeline.py \
    --raw "<raw_attendance.xlsx>" \
    --roster "<confirmed_roster.xls>" \
    --rules "<skill_path>/config/考勤规则.json" \
    --exclusions "<skill_path>/config/exclusions.json" \
    --template "<skill_path>/template/attendance_template.xlsm" \
    --out-dir "./交付"
  ```

### 步骤 5：交付文件产出检查与审计汇报
验证交付目录中是否包含完整的交付件：
- `考勤数据+排名-YYYY年MM01-MMDD- v1.0.xlsx`（单一干净版）
- `全量_考勤数据+排名-YYYY年MM01-MMDD- v1.0.pdf`（14 页）
- `重点关注_考勤数据+排名-YYYY年MM01-MMDD- v1.0.pdf`（1 页）

汇报模版：
> **【YYYY年MM月 考勤月报交付全部完成】**
> - **人员名单核验结果**：
>   - 原始打卡底表：XX 人
>   - 最终北京在册统计：**XX 人**（重点关注 X 人，游戏 XX 人，职能 XX 人，影视 X 人，虚拟 X 人，新业务 X 人，洪恩 XX 人）
> - **异常与预警统计**：
>   - 触发单向异常打卡标红：共 XX 处（其中 X 处经 Gate 3 确认已标黄）
>   - 触发均工时偏差标红预警（G - F > 0.5）：共 X 人
> - **交付成果物**：
>   - 交付 Excel：`交付/考勤数据+排名-YYYY年MM01-MMDD- v1.0.xlsx`
>   - 全量 PDF：`交付/全量_考勤数据+排名-YYYY年MM01-MMDD- v1.0.pdf`
>   - 重点关注 PDF：`交付/重点关注_考勤数据+排名-YYYY年MM01-MMDD- v1.0.pdf`
