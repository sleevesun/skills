# archive-project · 项目总结归档与知识回流

把项目（整体完成或阶段性完成）提炼为结构化知识，回流到知识库仓库。核心原则：**只回流提炼后的知识，不搬运原始文件；提炼在项目仓完成，提交在知识库仓完成。**

## 执行清单

```
- [ ] 1. 扫描项目素材
- [ ] 2. 生成复盘报告（固定模板）
- [ ] 3. 用户确认复盘内容
- [ ] 4. 定位知识库仓并 pull 最新
- [ ] 5. 按落点规则写入知识库
- [ ] 6. 调 submit-knowledge 流程提交推送（含关联检查）
```

## Step 1：确定总结模式并扫描素材

先根据用户表述判断模式，拿不准就问一句：

| 模式 | 触发示例 | 差异 |
|------|---------|------|
| **结项归档** | "项目归档""做完了""上线了帮我总结" | 报告进历史归档，04 模块状态改为已上线/已验收 |
| **阶段性总结** | "总结当前知识""阶段性总结""沉淀一下目前的进展" | 报告进进行中项目目录，04 模块保持进行中，聚焦本阶段增量 |

然后按优先级收集信息源：

1. 项目仓 `.knowledge/` 目录（执行过程中沉淀的决策记录，最可靠）
2. 项目目录下的 PRD、会议纪要、方案文档
3. 该项目的既有总结/复盘报告（阶段性总结必须先读上一份，只写增量）
4. 必要时询问用户补充：本阶段范围、上线日期、遗留问题

扫描后向用户汇报：确认的模式、找到多少份材料、时间跨度，确认总结范围。

## Step 2：生成总结报告（固定模板）

严格按此模板产出。文件名：
- 结项归档：`日期-项目名-复盘报告.md`（如 `20260817-试用期转正-复盘报告.md`）
- 阶段性总结：`日期-项目名-阶段总结-阶段名.md`（如 `20260817-试用期转正-阶段总结-需求与开发期.md`）

```markdown
# <项目名> <复盘报告/阶段总结>

## 基本信息
- 项目周期：<开始 ~ 结束/当前日期>
- 涉及系统：<HCM、绩效系统等>
- 项目状态：<已上线 / 已验收 / 暂停 / 进行中-阶段N>
- 本阶段范围（仅阶段性总结）：<本次覆盖的工作内容>

## 项目背景
<2~4 句：为什么做、解决什么问题>

## 关键决策
| 决策 | 原因 | 放弃的备选方案 |
|------|------|--------------|
| ... | ... | ... |

## 口径与配置变化
<本项目引入或修改的数据口径、权限、参数；没有则写"无">

## 时间节点
| 日期 | 事件 |
|------|------|
| ... | 需求确认 / 开发完成 / 上线 / ... |

## 遗留问题与后续计划
<未解决的问题、下一期计划；没有则写"无">

## 经验教训
<1~3 条对其他项目有复用价值的经验>

## 来源索引
- <本项目目录下的关键材料清单>
- <该项目的既往总结/复盘报告（如有）>
```

只写有文档依据的内容；材料中找不到的信息**标注"待补充"并询问用户**，不要编造。

## Step 3：用户确认

将完整总结报告展示给用户，确认后才进入回流步骤。用户修改意见直接更新报告。

## Step 4：定位知识库仓并 pull 最新

知识库仓识别（严格验证，不得猜测）：候选目录必须**同时满足**——含 `HR系统知识库/` 目录，且 `git remote -v` 输出包含 `cnb.cool/Chordsun/HRIS`。依次搜索当前目录与工作区其他根目录；不满足则**必须询问用户路径**；仍无法定位则提示 clone。禁止把同名/近名目录（knowledge_base、知识库、90_知识库 等）当作知识库仓——它们是项目本地资料目录，不是团队知识库仓。

```bash
cd <知识库仓路径>
git pull --rebase origin main
```

## Step 5：按落点规则写入知识库

复盘产出分流到三处：

| 产出 | 落点 |
|------|------|
| 时间节点与状态 | `HR系统知识库/04-项目进度与里程碑/` 项目总览：新增或更新该项目条目（阶段性总结保持"进行中"并标注阶段） |
| 口径与配置变化 | `HR系统知识库/07-配置参数与数据口径/` 对应文件，并追加口径变更记录 |
| 涉及系统的新功能/变更 | `HR系统知识库/02-功能模块详解/` 对应系统文件补充 |
| 上线/变更事件 | `HR系统知识库/06-系统变更历史/变更时间线.md` 追加条目 |
| 结项复盘报告（脱敏后） | `各系统历史文档/<年月-项目名>/` |
| 阶段性总结报告（脱敏后） | `进行中项目文档/<项目名>/` |
| 可复用的操作经验 | `HR系统知识库/03-操作指南与FAQ/` |

规则：
- 每个被修改的知识库文件，同步更新其"来源索引"（加入总结报告引用）
- 不确定的落点放 `收集箱/` 并在汇报中说明
- 更新 04/06 模块时保持既有条目格式，只追加或修改对应行
- 阶段性总结不改写结项才有的内容（如完整的经验教训可简写），避免与未来结项报告大量重复

## Step 6：调 submit-knowledge 流程提交推送

写入完成后，对知识库仓内的全部改动执行 submit-knowledge 的 Step 4~9（敏感扫描 → 大文件检查 → 关联检查 → 提交 → 推送）。commit 信息格式：

```
docs(总结-项目名): 归档项目复盘与知识更新      # 结项
docs(总结-项目名): 阶段总结（阶段名）与知识更新  # 阶段性
```

推送成功后向用户汇报：总结报告位置、更新了哪些知识库文件、commit hash。

## 敏感处理

- 总结报告与所有写入内容，一律经 submit-knowledge 的敏感扫描卡点
- 项目仓的原始文件（PRD 原件、纪要原件）**不复制进知识库仓**；若用户要求归档原件，走 submit-knowledge 完整流程单独处理
- 项目参与人姓名：总结中保留岗位角色即可，避免罗列个人明细

## 中途失败处理

知识库写入一半失败时：保留已写入的改动，明确告知哪些文件已改、哪些未改，下次继续时从断点接着做，不重复生成总结报告。
