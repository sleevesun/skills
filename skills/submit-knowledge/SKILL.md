# submit-knowledge · 知识入库提交

将材料提交到知识库仓库（GitLab 单仓库，main 分支直推，提交即生效）。本 Skill 是唯一守门员：所有校验在此完成，命中硬卡点必须中止。

## 执行清单

复制此清单并逐步跟踪进度：

```
- [ ] 1. 环境检查（git status / pull）
- [ ] 2. 材料分类与目录归位
- [ ] 3. 命名校验
- [ ] 4. 敏感扫描【硬卡点】
- [ ] 5. 大文件检查
- [ ] 6. 摘要生成（二进制文档）
- [ ] 7. 关联检查（涉及知识库文件时）
- [ ] 8. 规范提交
- [ ] 9. 推送 main
```

## Step 1：环境检查

知识库仓识别（严格验证，不得猜测）：
1. 候选目录必须**同时满足**：含 `HR系统知识库/` 目录，且 `git remote -v` 输出包含 `cnb.cool/Chordsun/HRIS`
2. 当前目录不满足时，搜索工作区其他根目录；仍不满足则**必须询问用户路径**；仍无法获取则提示先 clone（仓库地址见仓库 README）
3. 禁止把同名/近名目录（knowledge_base、知识库、90_知识库 等）当作知识库仓——它们是项目本地资料目录，不是团队知识库仓

```bash
git status --porcelain   # 有未提交改动时先询问用户如何处理
git pull --rebase origin main
```

## Step 2：材料分类与目录归位

| 材料类型 | 目标目录 |
|---------|---------|
| 在途项目原始材料（PRD、纪要、方案、Excel） | `进行中项目文档/<项目名>/` |
| 历史归档材料 | `各系统历史文档/<年月-项目>/` |
| 对知识库结论的修订或新增 | `HR系统知识库/` 对应模块（01~07） |
| 拿不准 | `收集箱/` |

判定不了归属时**一律放 `收集箱/`**，不要新建目录。

修订知识库文件的附加规则：
- 必须同步更新该文件内的"来源索引"段落
- 涉及数据口径变化的，在该文件的"口径变更记录"中追加一行：`日期 | 变更内容 | 原因`

## Step 3：命名校验

规范格式：`日期-项目-文档类型-版本`，例如 `20260814-试用期转正-会议纪要-v1.docx`。

- 日期取材料产生日期（8 位数字 YYYYMMDD），未知则取今天
- 不合规则自动重命名，**重命名结果必须先给用户确认**再继续
- 禁止出现"最终版""新建文档""副本"等字样

## Step 4：敏感扫描【硬卡点，不可跳过】

对每个待提交文件逐项检测：

| 模式 | 判定 |
|------|------|
| 18 位身份证正则 `\d{17}[\dXx]` | 命中即中止 |
| 银行卡号（13~19 位连续数字） | 命中即中止 |
| 关键词 `token` `secret` `password` `密码` `access_key` | 命中即中止 |
| 人名与"薪/工资/元/月/补偿金"在同一表格或相邻段落共现 | 命中即中止 |

命中处理流程：
1. 列出命中的文件名与位置
2. **立即中止**，不提交
3. 给出脱敏建议（替换为岗位/编号、删除明细列等）
4. 询问用户：脱敏后重试，还是放弃提交

用户声称"已脱敏/可以提交"时仍需复核命中项，确认是误报（如测试数据、编码）才可放行。

## Step 5：大文件检查

- 单文件 > 50MB：拒绝入库。提示用户存公司云盘，在仓库中放一个 `.md` 链接文件（含文档标题、存放位置、日期）
- 视频文件一律不入库，同上处理

## Step 6：摘要生成（二进制文档）

对 PDF / PPT / Excel / Word 文件，自动生成同名 `.md` 摘要（3~5 行）：

```markdown
# <文档标题>

- 日期：<产生日期>　类型：<会议纪要/PRD/方案/...>
- 主题：<一句话概括>
- 关键结论：<1~3 条>
- 涉及系统：<如 HCM、绩效系统等>
```

**摘要内容必须给用户确认后才继续。**

## Step 7：关联检查（仅当涉及知识库文件时）

若本次在 `HR系统知识库/` 有新增或修订，提交前必须执行：

1. 在知识库内检索与本次内容主题相关的既有文件（同一系统、同一口径、同一项目主题）
2. 新内容中添加指向相关文件的链接（相对路径，如 `../05-权限配置与角色定义/角色定义.md`）
3. 在被关联文件的相关段落补一条反向引用，保持双向可溯
4. 若新增了知识文件：同步在所属模块的总览文件与 `README.md` 导航中登记
5. 运行链接校验确认无失效：`python3 scripts/verify_links.py`

检索不到相关文件时如实说明，不要硬造链接。校验脚本报失效链接时先修复再继续。

## Step 8：规范提交

commit 信息格式：

```
docs(模块/项目): 一句话说明

# 示例
docs(202601-试用期转正): 新增面审会议纪要 20260814
docs(05-权限): 更新 SSC 岗位权限至 2026-08 版
```

括号内为模块或项目名，与目标目录对应。提交前用 `git diff --cached --stat` 向用户展示将提交的文件清单并确认。

## Step 9：推送 main

```bash
git push origin main
```

- 推送被拒（远程有更新）：`git pull --rebase origin main` 后重试；rebase 出现冲突则停下请用户决定
- 推送成功后告知用户：文件名、落位目录、commit hash
- 若本次修订了知识库文件，提醒用户：其他人下次 pull 即可获取

## 红线（永不入库）

- 员工姓名与薪酬/身份证/银行卡号的组合明细
- 账号、密码、token、密钥等凭证
- 确需保留的敏感材料：提示用户先脱敏，或联系仓库维护者评估受限存放

## 中途失败处理

任何一步失败或用户取消：保留已做的文件改动不提交（除非用户要求撤销），告知当前状态与卡点原因。
